# ADR-0001: Amazon EKS as the container platform

**Status:** Accepted

## Context
The platform runs several containerised services and needs autoscaling, progressive delivery, admission policy and a GitOps workflow. The target role centres on Kubernetes on AWS.

## Decision
Use **Amazon EKS** with API-mode authentication (access entries), managed add-ons (VPC CNI, CoreDNS, kube-proxy, Pod Identity agent), and a public API endpoint restricted to IAM-authenticated principals.

## Consequences
- The whole CNCF ecosystem is available: Argo CD/Rollouts, Karpenter, Kyverno, Prometheus operator. The platform is portable in design.
- Fixed control-plane cost ($0.10/h) and more moving parts than ECS: we operate the add-ons, and pay for that in upgrades.
- The public endpoint lets GitHub-hosted runners and the presenter's laptop reach the API. Production would use a **private endpoint** with self-hosted runners in the VPC (or CI that never touches the cluster, which is already true for app delivery).

## Alternatives considered
- **ECS on Fargate**: less to operate and no control-plane fee. But there is no ecosystem for GitOps, policy or canary analysis on par with Kubernetes, and it fits the role's requirements less well.
- **EKS Auto Mode**: AWS runs Karpenter, CNI and storage for you. It is attractive for real teams, but it adds a per-instance management fee and hides the components this project is meant to demonstrate. It stays the default recommendation for a small team with no platform engineers.
